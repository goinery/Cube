# 二、真实 3×3×3 魔方

必须构建一个真正具有真实魔方空间关系的 3×3×3 魔方。

不能只是一个立方体表面贴六张图片。

不能只是 27 个完全相同的普通小方块简单拼接。

必须明确区分：

- Corner / 角块
- Edge / 棱块
- Center / 中心块
- Core / 核心
- Sticker / 彩色外壳或贴片
- 必要内部连接结构

Corner、Edge 和 Center 应具有明显不同的形态和内部结构。

所有转动必须严格符合真实 3×3×3 魔方规则。

任何时刻都必须正确表达：

- 每个 Corner 当前的位置
- 每个 Corner 当前方向
- 每个 Edge 当前的位置
- 每个 Edge 当前方向
- 六个 Center 的关系
- 每个 Sticker 当前所在位置
- 每个 Sticker 当前方向
- 当前完整魔方状态

摄像机旋转、缩放、Explode、模型间距、材质变化、外观编辑等视觉操作不能改变真实魔方状态。

# 七、参数化 Exploded View

- Cubie Size
- Sticker Offset
- Internal Component Separation
- Animation Speed
- Easing

Explode 过程中：

- 不随机漂浮
- 尽量避免零件明显穿插
- 不破坏真实魔方状态
- 支持连续变化
- 支持平滑动画
- 支持反向聚合
- 支持一键恢复正常状态

完全展开后，整体应接近：

**高端消费电子产品 Teardown / Exploded Product Render**

的视觉质量。

支持标准 3×3 notation。

至少支持：

R R' R2  
L L' L2  
U U' U2  
D D' D2  
F F' F2  
B B' B2

提供 Algorithm 输入框。

用户可以输入例如：

R U R' U'

系统能够：

- Parse
- Validate
- Execute
- Animate
- Pause
- Resume
- Previous
- Next
- Restart
- 调整播放速度

输入错误 notation 时：

必须给出清晰错误提示。

# 二十三、Algorithm 播放器

算法输入后不能只是直接改变最终状态。

还应该提供完整动画播放器。

至少包含：

- Play
- Pause
- Resume
- Previous Move
- Next Move
- Restart
- Speed
- 当前 Move 高亮
- 已完成部分
- 待执行部分
- 当前进度

用户能够将任意合法算法作为 3D 动画逐步观察。

# 二十四、Scramble

提供一键随机打乱。

要求：

- 生成合法 3×3 Scramble
- 显示 Scramble Notation
- 支持动画执行
- 支持直接跳转到打乱后的最终状态
- 可以重新生成
- 可以复制 Scramble
- 打乱结果继续支持所有正常操作
- Solver 能够读取打乱后的状态

# 二十五、Undo / Redo / Reset

提供完整：

- Undo
- Redo
- Reset

Undo 和 Redo 必须能够正确处理用户实际执行的转层行为。

包括来自：

- 鼠标
- 触屏
- 键盘
- Algorithm
- Scramble
- Solver
- CFOP

Reset 应能够恢复到标准初始魔方状态。

最好进一步提供：

- Clear History
- Return to Scramble
- Replay History

# 二十六、合法魔方状态

任何真实魔方操作都必须始终保持合法。

如果应用允许用户通过导入状态或其它方式输入魔方状态，则必须能够识别物理上不可能出现的状态。

出现非法状态时：

需要给用户明确提示。

不能让 Solver 对明显非法的状态输出一个看似正常但实际上错误的解法。

# 二十七、Solver 总体要求

提供真正可以读取当前魔方状态并生成还原方案的 Solver。

Solver 结果不能只是一串文字。

必须可以：

- 显示解法
- 显示总步数
- 逐步播放
- 自动播放
- 暂停
- 继续
- Previous
- Next
- Restart
- 调节速度
- 高亮当前 Move

Solver 运行期间，用户应该能够清楚看到当前状态。

# 二十八、Fast Solver

提供：

**Fast / 快速求解**

该模式目标是：

快速得到一个较短且合法的还原方案。

优先保证：

- 响应速度
- 稳定性
- 实际可用性

不需要保证 mathematically optimal。

界面必须准确标注为：

**Fast**

或：

**快速求解**

不要错误标注为“最优”。

# 二十九、Near-optimal Solver

提供：

**Near-optimal / 近优求解**

目标是：

在合理时间内尽量寻找比 Fast 更短的方案。

可以允许等待时间比 Fast 更长。

但除非能够真正保证，否则不得声明这是绝对最短解。

界面应明确标注：

**Near-optimal**

或：

**近优解**

# 三十、Optimal Solver

如果产品实际具备真正意义上的最优求解能力，可以提供：

**Optimal / 最优解**

只有在确实能够保证所声明标准下的最优性时，才能使用这个名称。

如果无法保证：

不要为了功能看起来更强而错误标注为 Optimal。

可以隐藏该模式或明确说明实际能力。

准确描述实际求解能力比虚假宣传更重要。

# 三十一、CFOP 一键还原

提供独立的：

**CFOP Solve**

模式。

CFOP 应按人类常见 CFOP 流程展示，而不是把普通 Solver 的结果换一个名字。

至少需要体现以下阶段：

1. Cross
2. F2L
3. OLL
4. PLL

用户点击 CFOP 后，可以观察完整还原过程。

# 三十二、CFOP 阶段可视化

CFOP 求解过程中需要清晰显示：

- 当前阶段
- 当前 Algorithm
- 当前 Move
- 已完成阶段
- 剩余阶段
- 当前进度

支持：

- 自动播放
- 暂停
- 继续
- Previous
- Next
- Restart
- 调节播放速度
- 单步播放
- 重新播放当前阶段

阶段切换时需要有清晰但克制的视觉提示。

用户应该能够把 CFOP 模式当作真正的可视化教学工具。

# 三十三、求解过程 3D 动画

Fast、Near-optimal、Optimal（若实际支持）和 CFOP 都必须能够通过真实 3D 转层动画观察。

不能：

点击 Solve 后直接瞬间变成复原状态。

用户必须能够看到真实的：

- 一步一步转动
- 当前执行层
- 当前 notation
- 当前整体状态
- 求解进度

动画结束后：

3D 魔方、Cube Net、Hidden Face Mapping 和 Six Face Overview 必须同步显示正确最终状态。

# 三十四、操作模式

为了避免不同交互发生冲突，界面应清晰体现用户当前处于什么功能场景。

至少推荐包含：

- Play
- Camera
- Explode
- Customize
- Solver
- Inspect

用户应始终知道：

当前拖动是在：

- 转魔方
- 转摄像机
- 选择 Sticker
- 调整拆解效果
- 查看部件

不同模式之间应具有明确视觉反馈。

# 三十五、转层动画品质

所有层转动动画需要：

- 平滑
- 精确
- 有重量感但不过分缓慢
- 响应直接
- 动画结束时准确归位
- 连续多次操作后仍保持整齐

不应该出现：

- Cubie 逐渐错位
- 层间缝隙越来越歪
- Sticker 发生漂移
- 长时间操作后整体不再对齐

Scramble、Algorithm、Solver 和手动操作的动画品质应保持一致。

# 三十六、Explode 与真实魔方操作关系

Explode 仅改变视觉上的零件分离效果。

不能改变魔方本身逻辑状态。

即使当前处于：

- explode = 1
- explode = 2
- explode = 3

以下内容仍必须正确：

- CubeState
- Sticker 状态
- 图片方向
- Hidden Face Mapping
- Six Face Overview
- Cube Net

如果产品允许在一定拆解程度下继续转层，则转层必须仍然逻辑正确。

如果某些拆解程度不适合继续转层，则 UI 应明确提示当前状态。

# 三十七、自定义内容保存

复杂外观编辑不能因为刷新页面就全部丢失。

用户应能够保存并恢复：

- 当前配色
- 当前六面图片
- 54 Sticker 配置
- 多 Sticker 图片组
- 图片裁切
- 图片方向
- 当前魔方状态
- 当前外观方案

建议支持：

- Save
- Load
- Import
- Export
- Preset
- Restore Default

进一步可以支持分享当前魔方配置。

# 三十八、实时编辑预览

进行颜色、图片和 Sticker 编辑时：

3D 魔方必须实时显示结果。

对于整面图片：

需要能够同时清楚看到：

- 原始图片
- 当前裁切区域
- 3×3 分割
- 每个 Sticker 对应图片区域
- 3D 魔方最终效果

用户调整：

- 缩放
- 裁切
- 偏移
- 旋转

时，应获得实时反馈。

# 三十九、图片自定义与所有功能兼容

自定义图片必须与整个应用完整兼容。

包括：

- 手动转层
- Scramble
- Algorithm
- Undo
- Redo
- Reset
- Solver
- CFOP
- Hidden Face Mapping
- Six Face Overview
- Cube Net
- Exploded View
- 摄像机旋转
- 状态保存
- 状态恢复

不能只在魔方复原状态下图片正确。

打乱和求解过程中仍然必须保持物理方向正确。

# 四十、展示模式

应用除了“玩魔方”以外，也应具有高级产品展示能力。

建议提供：

- Hide UI
- Presentation Mode
- Fullscreen
- 自动旋转展示
- 标准产品展示角度
- Exploded View 展示
- Reset View
- Fit to View

使应用能够用于：

- 产品展示
- 魔方定制展示
- 机械结构展示
- 图片魔方展示
- 教学
- 演示

# 四十一、界面设计

整体 UI 必须与旗舰工业产品展示相匹配。

推荐视觉方向：

- 极简
- 精密
- 高级
- 现代
- 克制
- 中性
- 有足够留白
- 清晰信息层级
- 精细过渡动画

允许采用高级的深色或中性色界面。

可以适量使用半透明面板。

但不能让 UI 抢走 3D 魔方的视觉中心。

避免：

- 游戏化廉价 UI
- 过量霓虹
- 大面积彩色渐变
- 花哨背景
- 过多发光
- 过多装饰
- 按钮堆积
- 复杂控制台感

3D 魔方始终应该是视觉主角。

# 四十二、主界面信息架构

用户应该能够快速找到核心功能。

建议将主要功能清晰组织为：

- Play
- Scramble
- Undo
- Redo
- Reset
- Algorithm
- Solver
- CFOP
- View
- Hidden Faces
- Cube Net
- Explode
- Customize
- Settings

不要求必须使用上述具体布局。

但最终界面不能因为功能较多而显得混乱。

复杂控制应合理收纳。

常用操作必须容易访问。

# 四十三、当前状态反馈

界面应清晰显示重要状态。

例如：

- 当前 Mode
- 当前 Scramble
- 当前 Algorithm
- 当前 Move
- 当前 Solver
- 当前 CFOP 阶段
- 当前播放进度
- 当前播放速度
- 当前 Explode Amount
- 当前 View Mode
- Undo 是否可用
- Redo 是否可用

所有重要操作都需要获得明确但克制的反馈。

# 四十四、移动端界面

手机端不能只是简单把桌面 UI 缩小。

需要针对：

- 竖屏手机
- 横屏手机
- 小尺寸平板
- 大尺寸平板

重新合理组织操作界面。

移动端仍然必须完整支持核心能力。

复杂面板可以使用：

- Drawer
- Bottom Sheet
- Tabs
- Floating Toolbar
- Collapsible Panel

等适合触屏的表现形式。

具体实现不限。

最终要求是：

功能完整、可触控、可理解、不拥挤。

# 四十五、桌面端体验

桌面端应充分利用大屏幕空间。

可以让：

- 中央 3D 魔方占据主要区域
- 辅助面映射分布在周围
- 控制面板位于侧边
- Algorithm / Solver 具有专门区域
- Cube Net 和 Six Face Overview 有足够空间

但整体仍应保持干净和产品感。

不能因为功能多而变成开发工具界面。

# 四十六、加载体验

网页首次打开不能长时间保持空白。

需要有完整的加载体验。

至少体现：

- 产品 Loading
- 资源正在准备
- 模型加载进度或状态
- 加载完成后的自然过渡

应尽可能优先让用户快速进入可交互状态。

对于非首屏必要的高精度拆解细节，可以稍后进入完整品质。

用户不应因为高级模型资源而长时间面对没有反馈的空白页面。

# 四十七、运行流畅度

最终网页必须具有良好的实时交互体验。

正常操作中：

- 摄像机旋转流畅
- 缩放流畅
- 层转动流畅
- Scramble 动画流畅
- Solver 动画流畅
- Exploded View 调整流畅
- 图片编辑预览流畅
- UI 操作响应及时

视觉品质不能建立在严重卡顿的基础上。

不同性能设备可以自动采用不同视觉质量。

但不能因此降低：

- 魔方逻辑正确性
- Sticker 正确性
- Solver 功能
- Exploded View 核心能力
- 图片方向正确性
- 移动端操作能力

# 四十八、网页部署要求

最终必须交付为可实际运行的 Web 应用。

用户应能够通过现代网页浏览器直接访问。

无需安装专用客户端。

最终需要完整支持：

- Desktop Web
- Tablet Web
- Mobile Web

部署后应该能够直接完成：

- 玩魔方
- 转层
- 打乱
- 求解
- CFOP
- 图片定制
- Exploded View
- 查看所有面
- 保存配置

不能只交付：

- 静态视觉稿
- 视频
- 截图
- 模型文件
- 半完成原型
- 不可操作 Demo
- 只有部分功能的展示页

# 四十九、最终品质标准

最终产品不得看起来像：

- Three.js 入门 Demo
- CodePen 示例
- 普通彩色立方体
- 学生练习项目
- 简单游戏道具
- 低精度模型
- 只靠灯光包装的普通 Box
- 只实现表面效果的概念稿

最终视觉目标应接近：

**高端消费电子产品官网中的实时 3D 产品展示。**

同时还必须真正具备：

**可以完整游玩的真实 3×3×3 魔方逻辑。**

并同时满足四个核心标准：

### 1. 看起来像旗舰产品

正常浏览和近距离观察都具有高级产品质感。

### 2. 玩起来像真实魔方

转层、打乱、Undo、Redo、Solver 全部符合真实 3×3×3 魔方规则。

### 3. 拆开后像真实机械产品

内部零件、核心、磁力组件和连接结构具有可信机械逻辑。

### 4. 自定义和求解真正可用

图片、照片、54 Sticker、多 Sticker 图片、Solver、CFOP 和实时辅助映射都不是装饰功能，而是实际可使用功能。

# 五十、最终完成状态

当应用开发完成并成功运行后，应直接提供完整可用版本供人工体验和验收。

不要求额外提供自动测试系统或自动化验收流程。

最终验收由实际运行效果决定。

重点检查：

- 是否能够正常打开网页
- 是否能够完整操作魔方
- 视觉是否达到旗舰产品级
- 转层是否正确
- 打乱是否正确
- Undo / Redo 是否正确
- Solver 是否真实可用
- CFOP 是否真实按阶段播放
- 54 Sticker 是否可编辑
- 多 Sticker 是否可组成完整图片
- 图片在打乱和还原后方向是否正确
- Hidden Face Mapping 是否实时同步
- Cube Net 是否同步
- Exploded View 是否达到产品级拆解效果
- 手机和平板是否真正可操作
- 页面整体是否达到可实际展示和使用的产品完成度

最终目标：

> **打造一个真正运行在网页中的旗舰级 3D 魔方数字产品。它同时是一台真实魔方模拟器、一件高端工业产品的实时数字孪生、一个机械拆解展示工具、一个照片与图案魔方定制工具，以及一个可视化魔方求解与 CFOP 教学系统。**
